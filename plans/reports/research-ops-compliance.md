# Research: Rules/compliance, Failure modes, Operational reality (as of 2026-10-07)

Evidence caveat: WebFetch failed in this session (tool error); all facts below come from WebSearch summaries. Items marked [VERIFY] are from third-party/secondary sources or unconfirmed.

## 1. FINDINGS (what a competent solution MUST cover)

1. **Model lifecycle is the #1 risk, and it has already happened.** OpenAI Videos API / all Sora 2 endpoints (sora-2, sora-2-pro and snapshots) were shut down 2026-09-24 (announced 2026-03-24), no official replacement; /v1/videos reportedly 404s [VERIFY via OpenAI deprecations page]. Google announced deprecation of Imagen 2.x-4.x and Veo 2.x/3.0 GA endpoints on Vertex (migrate to Gemini image models / Veo 3.1 by 2026-06-30); Gemini API Imagen 4 reportedly gone 2026-08-17 [VERIFY, secondary]. OpenAI repointed gpt-image-1-mini/1.5 aliases to gpt-image-2 (2026-06-02). Vertex AI also being rebranded "Agent Platform"; old vertexai.* SDK modules removal 2026-06-24. => Model registry must be data (versioned JSON/DB), not code: per-model status (active/deprecated/sunset date), capability schema, price, replacement hint; a "model health/smoke test" and sunset warnings in UI; history items must keep the exact model ID + still render when model is gone.
2. **Auth differs sharply per provider; keep it behind a provider adapter.** Vertex: service-account JSON / ADC (gcloud) for Imagen/Veo; express-mode API key reportedly Gemini-models-only [VERIFY Veo/Imagen]. Gemini Developer API (ai.google.dev) is a separate, simpler key path with different quotas/retention. OpenAI: gpt-image-x requires Organization Verification (Persona ID check) per secondary sources [VERIFY]; error "must be verified" is a common first-run failure -> onboarding check. BytePlus ModelArk: API key + region endpoint (international ap-southeast), Seedance 2.0/2.5 access is not guaranteed self-serve in every geography/account [VERIFY]. Key storage: server-side only, never sent to browser; OS keychain (macOS Keychain / libsecret via keytar-like) or encrypted-at-rest file with master key from keychain; env-var fallback; redact in logs; prefer ADC over downloaded SA JSON; scoped least-privilege SA (aiplatform.user + objectAdmin on one bucket).
3. **All video (and slow image) is async with expiring output -> own the bytes.** Veo: long-running op, poll; Vertex writes to a GCS `storageUri` you supply (needs bucket, IAM, lifecycle rule); Gemini API Veo videos kept only 2 days. Sora links lasted ~1h [secondary]. ModelArk: create/get/list/cancel-delete task; result URL expiry reportedly short (24h unconfirmed) [VERIFY]. Pipeline: submit -> persist job row (provider op ID, params hash, idempotency key) BEFORE returning -> poll with jittered backoff -> on success download immediately to local store -> checksum -> thumbnail/poster -> mark done. Must survive restart (resume polling from persisted op IDs). No reliable webhooks for local-first app (Veo/ModelArk are poll-based) -> polling is default.
4. **Rate limits/concurrency are provider- and tier-specific.** Example documented: seedance-1.0-pro 10 concurrent tasks per model, 600 RPM on create (over-concurrency queues; over-RPM errors). Need per-provider+model token-bucket + concurrency semaphore, configurable, 429/RESOURCE_EXHAUSTED -> exponential backoff w/ jitter and honor Retry-After; distinguish quota (retry later) vs. safety block (don't retry) vs. 4xx invalid param (don't retry). Idempotency: client-side job IDs; provider submit is usually NOT idempotent -> persist "submitting" state before call and reconcile (risk of double-charge on crash between submit and persist; list-tasks API on ModelArk helps reconcile). Partial batch failure is normal: N variants = N independent jobs with batch aggregate status; retry-failed-only; cancel = best effort (cancel API exists on ModelArk; Veo/Vertex cancel support [VERIFY]; always may still bill).
5. **Cost control must be built in, not bolted on.** Pricing models differ: gpt-image-2 token-based (list: $8/M image-in, $30/M image-out, $5/M text-in; per-image ~ $0.006 low/$0.053 med/$0.211 high at 1024^2 are estimates; reference images always high fidelity -> more cost); Seedance token-based (1.0 Pro $2.5/M; 2.0 ~$3.3-4.3/M packs; 2.5 ~$6.4-10.7/M; tokens ≈ h*w*fps*dur/1024 [VERIFY]; charged only on success per BytePlus); Veo per-second, varies by model/audio/resolution. Need: versioned price table (editable, with "last verified" date), pre-run estimate shown as range with "estimate" label, per-batch confirm threshold, daily/monthly caps (hard stop), running ledger of estimated vs. actual (reconcile with provider billing: GCP Billing export, OpenAI usage/costs API), and failed/blocked requests may still cost. Prices change -> stale-price banner.
6. **Content policy: expect blocks, design for them.** Each provider filters prompts AND outputs; blocked results arrive differently (HTTP error vs. 200 with empty/filtered-count field, e.g. Veo returns RAI filtered info rather than a video; OpenAI `moderation` param auto|low only changes strictness, policy still applies). UI must normalize to a "blocked" state with provider reason, no auto-retry loop, no prompt-evasion helper. Person/likeness: Veo `personGeneration` is region/setting-gated; Seedance 2.x intercepts risky reference material and requires reference people to come from BytePlus's "private virtual portrait library" (Asset ID), and assets must not resemble real persons or infringe personality rights - uploading real-person photos as reference is effectively restricted [official docs; third-party claims of real-person support conflict]. Minors/celebrity/IP restrictions apply across all. Tool should: warn + require consent attestation checkbox when a reference image contains a real person, log it, and disable rather than circumvent.
7. **Provenance/watermarks are not optional to ignore.** Veo/Imagen/Gemini-image outputs carry SynthID (invisible; Veo 3.1 SynthID stated in Gemini API and Vertex); OpenAI reportedly attaches C2PA metadata [VERIFY official]; Seedance outputs may carry visible/implicit labels (China labeling rules; international behavior [VERIFY]). Implications: do not strip C2PA/watermarks; note that re-encoding/thumbnails/metadata writing can destroy C2PA manifest -> store pristine original untouched, put app metadata in a sidecar JSON (+ optional copy with embedded params), never rewrite originals. EU AI Act Art. 50 transparency obligations (applicable Aug 2026) push toward labeling AI content [VERIFY applicability to the user].
8. **Data retention/privacy/licensing.** OpenAI API: images endpoints kept up to 30 days for abuse monitoring; ZDR-eligible for gpt-image-x with caveats; Responses API image tool stores state 30 days by default; input images scanned for CSAM and retained if flagged. Vertex: governed by Google Cloud terms (no training on customer data by default; abuse-monitoring/caching nuances [VERIFY]); Gemini Developer API free tier differs (may use data) -> don't use free tier for client work. ByteDance/BytePlus: data processing in their regions, ToS must be read for commercial use/indemnity [VERIFY; not retrieved]. Commercial-use of outputs: generally permitted by paid API terms, but no copyright guarantee for AI output and no indemnity unless the provider offers it (Google offers IP indemnity for some Vertex gen-AI; [VERIFY scope]). Ship a per-model "terms notes" field and keep prompts/reference uploads classification (don't upload client-confidential imagery to third parties without consent).
9. **Month-6 failure checklist (build mitigations now).** (a) schema drift/params silently ignored -> adapter validates params against per-model capability schema, records "requested vs. effective params" from response, and warns on unsupported (e.g., seed/duration/resolution clamped); (b) seed nondeterminism: many models treat seed as best-effort; label "seed = hint, not guarantee", store output not just params for reproducibility; (c) long-video timeouts: polling timeout is per-job-configurable, 'stuck' state, resume; (d) huge files: stream downloads to disk (never buffer in memory), size/disk watermark guard, HTTP range + `<video preload="metadata">`; (e) gallery memory: thumbnails/posters generated server-side (webp ~ 256-512px), virtualized/paginated grid, never load full-res in grid, lazy video; (f) storage growth: disk usage meter, per-project size, trash with retention, optional archive/cold export, dedupe by sha256; (g) SDK churn: wrap provider SDKs or use thin REST clients; pin versions; contract tests recorded with VCR-style fixtures + a manual "live smoke test" button/CI cron; (h) DB: SQLite (WAL) + files on disk + schema migrations from day 1; (i) time/clock/regions: Vertex region availability per model differs (Veo not in all regions), GCS bucket should be in same region.
10. **Reproducibility metadata**: per output store sidecar JSON {provider, model id+version, full request payload (secrets redacted), response summary, effective params, seed, cost estimate/actual, timestamps, app version, input asset hashes, parent job IDs for flows}; optionally embed in PNG tEXt / XMP in a *copy*. Reference inputs must be copied/hashed locally so "re-run" works after the source is gone.

## 2. QUESTIONS FOR PRODUCT OWNER

1. **Who are the users and where does it run?** Why: decides key storage, auth, multi-user, compliance exposure. Options: (a) single user, localhost only; (b) small trusted team on one LAN/VPS server with shared keys; (c) hosted multi-tenant SaaS (changes everything: ToS reseller issues, KYC, per-user billing).
2. **Whose API keys and billing accounts?** Why: provider ToS often restrict sharing/reselling keys; spend attribution. Options: (a) each user brings own keys (stored per user); (b) one shared team key with per-user budgets; (c) org-owned keys managed by admin.
3. **Which Vertex auth path to support?** Why: SA JSON is a leaked-key risk; express-mode key may not cover Imagen/Veo. Options: (a) ADC/gcloud login only (dev-friendly); (b) SA JSON upload stored encrypted; (c) also support Gemini Developer API key as a simpler tier (different retention/quotas).
4. **Is Sora in scope given the API shutdown?** Why: Sora API is dead (2026-09-24); don't build an adapter. Options: (a) drop it; (b) keep a stub provider interface only; (c) replace with another video model (Veo 3.1, Seedance, Kling, Runway - name which).
5. **Seedance access route?** Why: BytePlus availability by country/account, onboarding KYC, 2.0/2.5 uncertainty, real-person restrictions. Options: (a) BytePlus ModelArk direct; (b) via aggregator (fal.ai, Replicate, etc.) with different terms/prices; (c) defer until access is confirmed. Has the owner got a working key/account already?
6. **Where do outputs live and how long?** Why: disk growth (videos are 10s-100s MB), expiring provider URLs. Options: (a) local disk only with usage cap + auto-trash; (b) local + S3/GCS mirror; (c) keep only thumbnails + params and re-download/regenerate on demand (not possible with expiring URLs -> reject).
7. **Budget policy?** Why: runaway batches (N variants x video) can be expensive. Options: (a) soft warning with confirm above $X; (b) hard daily/monthly cap per user/key; (c) both + require explicit confirm for any batch > N items or video > M seconds.
8. **How accurate must cost estimates be?** Why: price tables drift; some are token-based with unclear formulas. Options: (a) rough range from editable price table; (b) plus post-hoc reconciliation with provider usage/billing APIs; (c) no cost UI in v1 (not recommended).
9. **Real-person / likeness reference images: allowed?** Why: Seedance bans/restricts; Veo/OpenAI have policy on minors and public figures; legal consent. Options: (a) allow with a consent attestation + audit log; (b) block uploads detected as faces (extra dependency); (c) allow only provider-supported flows (e.g. Seedance portrait library) and warn elsewhere.
10. **Intended use of outputs: personal, client work, or published commercial content?** Why: terms, copyright uncertainty, EU AI Act/platform labeling, provenance. Options: (a) personal/experiments; (b) client/commercial with per-model terms notes shown in UI; (c) public publication with enforced provenance (keep SynthID/C2PA, add own disclosure).
11. **Provenance handling: preserve vs. embed?** Why: rewriting files can destroy C2PA. Options: (a) originals untouched + sidecar JSON; (b) also export copy with embedded params (PNG tEXt/XMP); (c) embed in originals (breaks C2PA, not recommended).
12. **Persistence & restart behavior of jobs?** Why: video takes minutes; user closes laptop. Options: (a) in-process queue, lost on restart (simple, bad); (b) SQLite-backed queue with resume of polling; (c) external queue (Redis/BullMQ, Celery) - heavier for local-first.
13. **Stack choice (Next.js/Node vs. Python backend)?** Why: Python has first-party google-genai/OpenAI SDKs and ffmpeg/Pillow tooling; Node unifies UI. Options: (a) Next.js + Node worker; (b) Python FastAPI backend + React UI; (c) Tauri/Electron wrapper for keychain access and offline-first.
14. **Provider-update policy: who maintains the model registry?** Why: deprecations (Sora, Imagen, Veo 3.0) will recur every ~6 months. Options: (a) manual editable JSON with sunset warnings; (b) auto-fetch model lists from provider list-models APIs and flag unknowns; (c) community/remote-updated registry file.
15. **Node-based flow chaining: how much of its failure semantics in v1?** Why: chaining multiplies cost, partial failures, and reproducibility needs. Options: (a) defer flows; (b) linear chains only with per-step caching and cost preview; (c) full DAG with node-level retry/caching.
16. **Reproducibility promise?** Why: seeds are best-effort. Options: (a) "params recorded, results not guaranteed"; (b) store full request + inputs for exact re-run attempt; (c) don't claim it.
